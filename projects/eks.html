01프로젝트 개요

한 개의 EKS 클러스터 위에서 13개 서비스 네임스페이스와 관리(Management) 스택을 Git 선언형으로 운영하는 환경입니다.

무엇을 운영하는가

  • Amazon EKS v1.34 단일 클러스터 (Private Endpoint)
  • 서비스 13개 네임스페이스에 67개 ArgoCD Application
  • 관리 스택: ArgoCD · Argo Rollouts · Istio · OpenTelemetry · Prometheus · Grafana · Loki/Tempo · Kiali · n8n · k6 Operator
  • 서비스 → 외부/RDS 접근 통제용 Istio ServiceEntry 54건

핵심 설계 원칙

  • Everything as Code — 서비스·관리 스택·알림 룰·ALB 설정까지 모두 Git 관리
  • Blue/Green 배포 — Argo Rollouts 로 preview 확인 후 promote
  • 서비스별 진입 경로 분리 — 서비스마다 Istio IngressGateway + ALB 그룹
  • 노드그룹 격리 — nodeSelector.role 로 관리/서비스별 노드 분리
  • OTel 중심 관측 — metric / trace / log 를 한 흐름으로 수집
저장소 구조 — 한 저장소에서 클러스터 전체를 표현합니다.

02전체 아키텍처

외부 요청은 WAF → ALB → 서비스별 Istio IngressGateway → 서비스 Pod 로 흐르고, 외부 호출은 Egress / ServiceEntry 로 통제합니다.

03배포 방식 — GitOps

Git 이 단일 진실 공급원(SSOT)입니다. 클러스터 내 변경은 ArgoCD 가 Git 과 비교·동기화하며, 배포는 Argo Rollouts 의 Blue/Green 으로 진행합니다.

서비스 Application 표준 구조

  • 서비스 1개 = ArgoCD Application 1개, 차트는 서비스 저장소의 helm/ 를 참조
  • values-prd.yaml + version.yaml + rollout-version.yaml 3개 values 로 환경·이미지·롤아웃 버전을 분리
  • 노드그룹은 Application 의 helm.values 로 nodeSelector.role 을 주입 → 서비스 코드 변경 없이 노드 이전 가능
  • 네임스페이스당 namespace · project · application · efs-pv-pvc · setup.sh 5종 세트로 표준화
  • HPA 의 minReplicas/maxReplicas 는 ignoreDifferences 로 운영자 변경 허용

관리 스택 Application 표준 구조

  • 공식 Helm 차트(prometheus, n8n, grafana 등) + 멀티 소스: 차트는 외부 레포, values 는 $values/management/... 로 devops 저장소에서 참조
  • 차트 버전 고정 (예: prometheus 27.11.0, n8n 1.16.14, k6-operator 4.6.0)
  • values 를 용도별 파일로 분리 — values-custom / values-rules / values-scrape / values-alertrule
  • Helm 차트가 없는 Oracle Exporter 는 Deployment 매니페스트를 directory.include 로 별도 Application 화
  • Operator 계열(Istio, ArgoCD 본체, OTel Operator)은 Git 에 파일로 두고 istioctl / kubectl apply 로 반영

04트래픽 · 네트워크 설계

ALB Ingress(Group) → Istio IngressGateway → 서비스. 서비스/도메인 단위로 경로를 분리했습니다.

ALB 구성 방식

  • Ingress 어노테이션으로 ALB를 선언 — group.name, scheme, listen-ports, certificate-arn(ACM 다중), wafv2-acl-arn, ssl-policy
  • Internet-facing(WAF 연동) / Internal 분리
  • target-type: NodePort Service → instance, ClusterIP → ip 로 구분 적용
  • 비용 산정용 태그(Estimate) 를 ALB에 부여

Istio Gateway

  • 서비스별 IngressGateway(3종) 를 IstioOperator 로 정의
  • 각 게이트웨이 별도 HPA(min/max) 및 전용 노드그룹 nodeSelector
  • ALB 헬스체크 경로 /healthz/ready (status-port)
  • holdApplicationUntilProxyStarts 로 사이드카 기동 순서 보장

리다이렉트 · 라우팅

  • ALB actions 로 구 도메인 → 신 도메인 301 리다이렉트 (PC / 모바일)
  • 점검 페이지(PM) 전환용 redirect 액션
  • 호스트/경로 기반 규칙(예: 특정 path 별 백엔드), 서브도메인 session sticky
  • Webhook 처럼 외부 노출이 필요한 호스트만 Public Ingress 로 최소 개방

05관측(Observability) · 알림

OpenTelemetry 를 허브로 metric · trace · log 를 모으고, Grafana 알림 룰까지 YAML(Helm values)로 관리합니다.

Alert-as-Code (Grafana)

  • 대시보드 UI 에서 만들던 알림 룰을 values-alertrule.yaml 로 이전하여 Git 으로 관리
  • 그룹: service-resource-group(CPU/Memory) · service-group(Pod Restart, P95 Latency) · aws-rds-group · db-group(20 룰)
  • 2개 EKS 클러스터 대상 × Warning / Critical 단계
  • critical_level(RDS=1, 리소스/Pod=2, Latency=3) 로 원인 우선순위 부여 → 연쇄 알림 억제
  • alert_group, *_sync 라벨로 라우팅 기준 통일

DB 모니터링 확장

  • CloudWatch 로는 얻을 수 없는 DB 내부 지표(연결율, Running Threads, Thread Seconds 등)를 위해 Exporter 도입
  • mysqld_exporter 멀티타겟 — 파드 1개로 RDS 10대 probe, 타깃 추가는 scrape 목록만 수정
  • postgres_exporter 2벌(일반 RDS / Aurora) — Aurora 스토리지 복제 함수 오류로 별도 분리
  • oracledb_exporter — Helm 차트가 없어 Deployment 로 직접 구성
  • 수집 주기 60s → 30s, DBA 요청서(읽기전용 계정·권한 근거) 문서화

분산 트레이싱

  • Istio(Envoy) 트레이싱 대상을 OTel Collector 로 지정하고 access log 의 trace_id 노출을 검증, Collector → Tempo 로 저장
  • OTel Operator Instrumentation CR 로 언어별(Java / Node.js / Python) 자동 계측, 언어별 파일 분리
  • 로그의 trace_id 출처(OTel Java agent), 샘플링 정책(parentbased_traceidratio)과 수집량의 관계를 Q&A 문서로 정리 (2026.09)

Prometheus 룰 · 수집

  • Host / Kubernetes 표준 룰 세트 + Istio 4xx·5xx 에러율 룰
  • ArgoCD · Alertmanager 메트릭 scrape, 노드 request/limit 적정값 산출용 수집 추가
  • Prometheus 볼륨 증설, CPU Steal Time 지속 조건(20분) 조정

06내가 한 일 (Git 이력 기반)

역할별 정리

① 배포 · 트래픽 (Argo / Istio / ALB)

  • Argo Rollouts 를 매니페스트 방식에서 Helm 설치·관리 방식으로 전환, 대시보드 Ingress 및 네임스페이스 조회용 ClusterRole 구성
  • 서비스 도메인별 Istio IngressGateway + ALB Ingress 신규 구성 (3개 서비스), 외부·내부 ALB 분리
  • WAF·ACM 인증서·TLS 1.3 정책 반영, 서브도메인 session sticky, 비용 산정 태그
  • ServiceEntry 체계 정비 (resolution DNS / MESH_INTERNAL, 미사용 DB 정리, SMTP TLS) 및 신규 대상 일괄 등록
  • 서비스 신규 온보딩: 다수 서비스(배치·백오피스·파트너 등 하위 구성 포함)의 Application · PV/PVC · AppProject 작성
  • 13개 서비스 setup.sh 표준화 (namespace 선생성, PV/PVC 환경변수 매핑)

② 관측 (OTel / Prometheus / Loki / Grafana)

  • Istio 트레이싱 설정(OTel/Envoy)과 access log 포맷 변경, trace_id 노출 검증
  • OTel Collector 메트릭 라벨을 수차례 실험하며 불필요/중복 라벨 제거 (카디널리티 축소)
  • 언어별 자동 계측 설정(Java / Node.js / Python) 정리, Python 메트릭 export 옵션 통일
  • Loki Promtail level / service 라벨링, querier·query series 한도 조정
  • Grafana 알림 룰 Alert-as-Code 이전 및 임계치·그룹·라벨 체계 설계 (34 룰)
  • DB Exporter 4종(mysqld / postgres 2 / oracledb) 도입 + DB 알림 20룰 활성화
  • Grafana MCP 서버 PoC, Alertmanager 지표 scrape, Istio 5xx 룰 추가

③ 클러스터 운영 · 인프라

  • EKS 1.32 → 1.34 업그레이드 (Terraform + 노드그룹 교체 + Add-on 갱신 + 전 컴포넌트 nodeSelector 이전)
  • nodeSelector 체계 도입 — 관리/서비스 컴포넌트를 노드그룹별로 격리
  • 노드 스토리지 증설(80GB 노드그룹) 대응 전 서비스 반영
  • OTel Operator 이미지 레지스트리 변경 대응(kube-rbac-proxy), Grafana 플러그인 자동 업그레이드 방지
  • 사용하지 않는 서비스/설정/폴더 정리 (예: 한 번에 1,456 줄 삭제한 저장소 정합성 작업)

④ 자동화 · 문서화 · 품질

  • Jenkins 연동: 파라미터 기반으로 ArgoCD Application 매니페스트가 devops 저장소에 자동 생성되도록 샘플 서비스 구성 및 파라미터 정합
  • HPA 변경 허용을 위한 ignoreDifferences 도입 및 syncPolicy(RespectIgnoreDifferences) 검증
  • k6 Operator 구성, Grafana K6 대시보드, 개발팀 인수인계 문서 작성
  • 노드그룹 교체 런북, 트레이싱 Q&A, RDS 임계치·Exporter 도입 계획서, DBA 계정 요청서 작성
  • 알림 룰 변경 시 임시 임계치로 알림 흐름 테스트 후 원복하는 검증 절차 수행
